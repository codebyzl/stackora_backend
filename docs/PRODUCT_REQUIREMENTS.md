# Stackora 产品需求总览

## 1. 项目定位

Stackora 是一个从零开发的 Java 技术社区后端项目。

项目业务形态参考 Paicoding / 技术派，但目标不是复制源码，而是通过独立需求设计、独立编码、测试验证、代码评审和成熟项目对比，系统掌握真实后端项目开发。

本项目前期以后端为主，通过 Swagger / Knife4j、接口测试和自动化测试验证功能，不为了展示效果过早投入复杂前端。

## 2. 项目目标

Stackora 最终目标是形成一个可部署、可测试、可持续演进的技术社区后端系统。

长期能力包括：

- 用户注册、登录、退出、个人资料和权限校验。
- 文章发布、编辑、删除、详情、分页、分类和标签。
- 评论、回复、点赞、收藏和关注。
- 站内通知。
- Redis 缓存、排行榜和热点数据。
- Redisson 分布式锁与并发控制。
- RabbitMQ 异步通知。
- Elasticsearch 文章搜索。
- 后台审核和内容治理。
- 测试、日志、监控、Docker 部署和运维文档。

这些能力不会一次性实现。项目采用循序渐进路线：先完成稳定单体核心业务，再逐步补充缓存、消息队列、搜索和部署能力。

## 3. 用户角色

### 3.1 游客

游客可以浏览公开内容，例如文章列表、文章详情、分类列表和搜索结果。游客不能发布文章、评论、点赞、收藏或关注。

### 3.2 普通用户

普通用户可以维护个人资料，发布和管理自己的文章，评论和回复，点赞、收藏、关注用户，并接收站内通知。

### 3.3 管理员

管理员可以管理用户、审核内容、处理违规文章或评论，并执行平台治理操作。

## 4. 核心业务域

- 用户域：账号、资料、登录态、权限、用户状态。
- 文章域：草稿、发布、编辑、删除、详情、列表、状态。
- 分类标签域：文章分类、标签绑定、筛选和统计。
- 评论域：文章评论、回复、删除、审核。
- 互动域：点赞、收藏、关注、计数维护。
- 通知域：站内通知和异步事件处理。
- 搜索域：文章全文搜索和索引同步。
- 后台治理域：内容审核、用户治理、违规处理。
- 基础设施域：配置、异常、校验、测试、日志、部署。

## 5. 技术栈与引入阶段

### 5.1 V0：工程骨架

本阶段只建立最小可运行后端骨架，不实现具体业务。

计划使用：

- JDK 17
- Spring Boot 3.x
- Maven
- MySQL 8
- MyBatis-Plus
- Lombok
- Jakarta Validation
- JUnit 5
- Swagger / Knife4j
- SLF4J / Logback

本阶段关注：

- 项目能稳定启动。
- 配置按环境隔离。
- 能连接真实 MySQL。
- 有健康检查接口。
- 有统一响应和异常处理的基础设计。
- 不提交真实密码。
- 有最小测试。

### 5.2 V1：用户与认证

本阶段完成注册、登录、退出和当前用户闭环。

计划使用：

- HttpSession
- Cookie
- Spring MVC Interceptor
- 密码哈希
- 统一错误码
- 后端权限校验

MVP 阶段优先使用 Session，是为了先理解登录态、Cookie、拦截器和后端权限边界。JWT、Sa-Token、Spring Security 等方案不在第一版直接引入，除非经过单独设计评审。

### 5.3 V2～V5：核心业务闭环

本阶段完成文章、分类标签、评论、点赞收藏关注等核心业务。

重点技术包括：

- MySQL 表设计。
- 唯一索引和普通索引。
- 事务边界。
- 逻辑删除。
- 分页插件。
- Request / DTO / Entity / VO 分离。
- 所有者权限校验。
- 幂等与重复提交设计。

在这个阶段，MySQL 是核心业务数据的事实来源。缓存、消息队列和搜索引擎暂时不作为主流程依赖。

### 5.4 V6：缓存与并发扩展

Redis、Redisson 和分布式锁属于后续扩展阶段，不是项目一开始就引入。

计划在出现真实业务需求后再引入，例如：

- 热门文章缓存。
- 首页榜单或排行榜。
- 文章浏览量、点赞数等热点数据。
- 登录态 Redis 化。
- 防止重复提交。
- 高并发点赞、收藏或关注。
- 缓存穿透、缓存击穿、缓存雪崩治理。
- 缓存与 MySQL 的一致性策略。

Redisson 分布式锁只在单机锁无法解决问题，或者需要跨实例并发控制时引入。引入前必须明确：

- 要保护的共享资源是什么。
- 不加锁会发生什么并发问题。
- 锁的粒度是什么。
- 锁过期、续期和释放失败怎么处理。
- 是否存在更简单的数据库唯一约束或事务方案。

### 5.5 V7：消息队列与异步通知

RabbitMQ 属于异步能力扩展阶段，不在前期核心业务闭环中使用。

计划在以下场景出现后引入：

- 用户评论后异步通知文章作者。
- 用户点赞、收藏、关注后异步生成站内通知。
- 文章审核、搜索索引更新等操作需要异步解耦。
- 某些操作不应阻塞主请求。

引入 RabbitMQ 前必须设计：

- 消息生产失败怎么处理。
- 消息重复消费怎么保证幂等。
- 消息丢失如何发现和补偿。
- 消费失败如何重试。
- 业务最终一致性如何验证。

### 5.6 V8：搜索扩展

Elasticsearch 属于搜索能力扩展阶段。

计划在文章数量、搜索体验或全文检索需求明确后引入。

主要关注：

- 文章索引设计。
- 搜索接口。
- MySQL 到 Elasticsearch 的数据同步。
- 索引重建。
- 数据不一致时的修复策略。

### 5.7 V9～V10：治理与部署

后期逐步补充：

- 后台审核。
- 用户封禁。
- 内容治理。
- Docker。
- Docker Compose。
- Nginx。
- 生产配置隔离。
- 健康检查。
- 日志规范。
- 基础监控。
- 部署与回滚文档。

## 6. 架构原则

- 先采用清晰的单体分层架构。
- 不为了“高级”而过早拆微服务。
- Controller 只处理请求接收、鉴权入口和响应封装。
- Service 负责业务规则和事务。
- Mapper 负责数据库访问。
- Entity 不直接作为公开接口返回。
- VO 只暴露前端需要的数据。
- MySQL 是核心业务数据的事实来源。
- 缓存不是事实来源。
- 所有重要写操作必须说明事务、幂等和并发策略。
- 数据库唯一约束是防止重复数据的最后防线。

推荐包结构：

```text
src/main/java/org/victor/stackora/
├── common/
├── config/
├── controller/
├── exception/
├── interceptor/
├── annotation/
├── aspect/
├── model/
│   ├── entity/
│   ├── dto/
│   ├── request/
│   ├── vo/
│   └── enums/
├── mapper/
├── service/
│   └── impl/
├── repository/
├── event/
├── mq/
├── search/
└── util/
```

`repository`、`event`、`mq`、`search` 等目录只有在真实需要出现后再使用，不提前空建复杂结构。

## 7. 项目文档结构

项目内文档建议组织为：

```text
docs/
├── PROJECT_IDENTITY.md
├── PROJECT_ROADMAP.md
├── PRODUCT_REQUIREMENTS.md
├── TECH_STACK.md
├── ARCHITECTURE.md
├── modules/
├── decisions/
├── api/
├── database/
├── reviews/
└── deployment/
```

各文档用途：

- `PROJECT_IDENTITY.md`：项目名称、仓库名、Maven 坐标、基础包名、数据库名。
- `PROJECT_ROADMAP.md`：版本路线和学习目标。
- `PRODUCT_REQUIREMENTS.md`：产品级需求总览和业务范围。
- `TECH_STACK.md`：技术栈、引入阶段和依赖选择理由。
- `ARCHITECTURE.md`：总体架构、分层边界和编码约定。
- `modules/`：每个模块的需求与技术设计。
- `decisions/`：重要技术决策记录。
- `api/`：接口约定和接口清单。
- `database/`：表结构设计说明和迁移记录。
- `reviews/`：模块评审、评分、Paicoding 对比和复盘。
- `deployment/`：本地、测试和生产部署说明。

这些文档属于 Stackora 项目的正式开发者文档，未来可以随 `stackora` 代码仓库一起提交。仓库文档只记录产品需求、技术设计、接口、数据库、部署和复盘内容。

## 8. 模块设计文档要求

每个新模块建议维护独立的需求与技术设计文档：

```text
docs/modules/YYYY-MM-DD-<module>-design.md
```

模块设计需要覆盖：

- 背景与用户价值。
- 本次实现范围。
- 本次不实现内容。
- 用户故事。
- 业务规则。
- 正常流程。
- 异常流程。
- 权限与数据归属。
- 数据模型。
- 唯一约束和索引。
- API 设计。
- Request / DTO / Response / VO 边界。
- 错误码。
- Controller 到 Service 到 Mapper 的调用链。
- 事务边界。
- 并发、幂等和重复提交。
- 安全与隐私。
- 测试设计。
- 验收标准。
- Paicoding 预对比点。
- 风险与技术债。
- 待确认问题。

模块设计文档用于统一业务边界、数据模型、接口契约和验收标准。

主要能力：

- Spring Boot 3 + Maven 项目。
- 配置隔离。
- MySQL 与 MyBatis-Plus 接入。
- 统一响应和异常处理。
- 参数校验。
- Swagger / Knife4j。

目标：完成注册、登录、退出和当前用户闭环。

主要能力：

## 10. 模块完成标准

一个模块只有同时满足以下条件，才算完成：

- 设计文档已经明确需求范围、接口契约、数据模型和验收标准。
- 实现符合已通过的设计。
- 正常业务流程可运行。
- 关键异常流程有明确响应。
- 后端权限校验生效。
- 数据库约束和索引已确认。
- 事务边界正确。
- 关键测试通过。
- 需要接口文档时，接口文档可用。
- 没有敏感数据泄露。
- 设计、评审和技术债记录已更新。
- 开发者能够解释核心调用链和设计原因。
