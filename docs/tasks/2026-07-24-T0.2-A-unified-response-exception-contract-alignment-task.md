# 2026-07-24 任务：T0.2-A 统一响应与异常处理契约对齐

## 1. 任务目标

完成统一响应与异常处理模块的契约对齐，使正式设计文档、公共类命名、错误码定义、异常转换规则和测试计划保持一致。

本任务最终支撑的工程能力是：后续业务接口可以稳定使用 `ApiResponse<T>` 返回成功结果，使用 `BusinessException` 表达可预期失败，并由 `GlobalExceptionHandler` 转换为真实 HTTP 状态和安全响应体。

预计用时：1～3 小时。

## 2. 用户价值

统一响应与异常处理会被用户、文章、评论、点赞、收藏等后续接口复用。若本模块的命名、业务码、HTTP 状态和测试规则不统一，后续接口会出现多套返回结构，调用方和维护者都难以判断错误原因。

## 3. 今日范围

- 将统一响应类命名固定为 `ApiResponse<T>`。
- 将统一响应工厂命名固定为 `ApiResponseFactory`。
- 将业务异常命名固定为 `BusinessException`。
- 将全局异常转换器命名固定为 `GlobalExceptionHandler`。
- 对齐 `ErrorCode` 的枚举名、业务码、默认消息和 HTTP 状态。
- 明确临时验证接口不得作为正式业务接口保留。
- 补充能验证统一响应与异常转换行为的 Web 层测试计划。

## 4. 今日明确不做

- 不实现用户、文章、评论或其他业务模块。
- 不修改数据库表、索引、SQL 或环境变量。
- 不引入 Redis、Redisson、RabbitMQ、Elasticsearch、Docker、Nginx 或前端能力。
- 不把临时 `/test` 接口作为正式 API。
- 不把只有编译通过、没有行为测试的结果作为模块完成依据。

## 5. 具体需求包

### 5.1 明确能力与交付物

- 统一响应体：
  - 类名：`ApiResponse<T>`
  - 属性：`code`、`message`、`data`
  - 成功：`code=0`、`message=ok`、HTTP `200 OK`
  - 失败：`data` 语义为 `null`，序列化时允许省略；HTTP 状态由错误类型决定
- 响应工厂：
  - 类名：`ApiResponseFactory`
  - 提供 `success(T data)`、`success()`、`error(ErrorCode errorCode)`、`error(ErrorCode errorCode, String safeMessage)`
- 错误码：
  - 包含业务码、默认安全消息和 HTTP 状态
  - 当前覆盖通用请求错误、参数错误、未登录、无权限和系统错误
- 业务异常：
  - `BusinessException(ErrorCode errorCode)`
  - `BusinessException(ErrorCode errorCode, String safeMessage)`
  - `safeMessage` 只能传递可公开给调用方的业务描述
- 全局异常转换：
  - 业务异常按 `ErrorCode` 转换
  - 参数校验、请求体解析和参数类型错误的专用映射随对应能力接入时实现
  - 未知异常返回 `500`

### 5.2 正常流程

1. Controller 接收请求并触发参数校验。
2. Controller 调用 Service。
3. Service 正常返回业务结果。
4. Controller 使用 `ApiResponseFactory.success(data)` 或 `ApiResponseFactory.success()` 返回统一响应。
5. 客户端收到 HTTP `200 OK` 和 `code/message/data` 三字段响应体。

### 5.3 异常流程

- Service 发现业务规则不满足时抛出 `BusinessException`。
- `GlobalExceptionHandler` 捕获业务异常，并使用异常中的 `ErrorCode.httpStatus` 设置 HTTP 状态。
- Bean Validation、JSON 请求体解析和参数类型转换的专用异常映射推迟到对应能力接入时实现。
- 未知异常记录服务端日志，客户端只收到通用系统错误消息。

### 5.4 权限与数据规则

- 本任务不实现认证与授权。
- 预留未登录和无权限错误码，供后续认证模块复用。
- 客户端错误响应不得包含密码、Token、Cookie、Session ID、完整 JDBC URL、SQL、服务器路径、异常堆栈或底层异常消息。
- 本任务不读写数据库，不涉及事务、幂等、缓存一致性或数据归属。

### 5.5 接口、配置和数据库要求

- 不新增正式业务接口。
- 如需验证异常映射，应使用测试专用 Controller 或测试配置，不长期保留临时 `/test` 接口。
- 实现参数校验时允许增加 `spring-boot-starter-validation`。
- 不修改 Actuator `/actuator/health` 与 `/actuator/info` 的标准响应结构。

## 6. 测试场景

- `ApiResponseFactory.success(data)` 返回 `code=0`、`message=ok` 和原始 `data`。
- `ApiResponseFactory.success()` 返回 `code=0`、`message=ok` 和 `data=null`。
- `BusinessException(ERROR)` 返回 HTTP `400` 和对应业务码。
- `BusinessException(errorCode, safeMessage)` 可以覆盖客户端消息，但不改变业务码和 HTTP 状态。
- 参数校验、JSON 解析和参数类型错误测试随对应能力接入时补充。
- 未知异常返回 HTTP `500`，响应不包含异常类名、堆栈、SQL 或服务器路径。
- `/actuator/health` 保持 Spring Boot 标准响应，不出现业务响应体的 `code` 和 `data` 字段。

## 7. 验收标准

- 正式设计文档与代码命名一致，统一采用 `ApiResponse` 和 `ApiResponseFactory`。
- `ErrorCode` 的枚举名、业务码、默认消息和 HTTP 状态与设计一致。
- `ApiResponseFactory.success` 成功响应使用业务码 `0` 和消息 `ok`。
- 全局异常转换至少覆盖业务异常和未知异常；实现参数校验后覆盖校验、请求体解析和参数类型错误。
- 临时 `/test` 接口不作为正式 API 保留。
- `./mvnw test` 执行时至少包含统一响应与异常处理相关测试，且测试数量大于 0。

## 8. Goal / Context / Constraints / Done when

**Goal**：完成统一响应与异常处理模块的命名、错误码和异常转换契约对齐。

**Context**：当前实现命名采用 `ApiResponse<T>`、`ApiResponseFactory`、`ErrorCode`、`BusinessException` 和 `GlobalExceptionHandler`，正式设计需要与该命名保持一致。

**Constraints**：只处理统一响应与异常处理模块；不推进新业务模块；不提交缺少行为测试的公共异常处理实现。

**Done when**：设计文档、代码草稿和测试计划使用同一套公共契约，并能通过自动化测试验证成功响应、业务异常、未知异常和 Actuator 兼容性。
