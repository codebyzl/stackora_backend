# 2026-07-23 任务：T0.2-A 统一响应与异常处理命名对齐

## 1. 任务目标

对齐统一响应与异常处理模块的设计命名、代码草稿命名和后续实现范围，确保后续实现围绕同一套 API 契约展开。

本任务不新增业务能力，重点是消除“设计文档使用一套名称、代码草稿使用另一套名称”的偏差。

预计用时：1～2 小时。

## 2. 用户价值

统一响应和异常处理是后续所有业务接口的公共基础。如果命名和职责在第一个公共模块就不统一，后续用户、文章、评论等模块会持续复制不一致的写法，增加维护和学习成本。

## 3. 当前命名差异

设计文档当前使用：

- `BaseResponse<T>`
- `ResultUtils`
- `BusinessException`
- `GlobalExceptionHandler`

当前代码草稿使用：

- `ApiResponse<T>`
- `ApiResponseFactory`
- `GlobalResponseException`
- `GlobalExceptionInterception`
- `TestController`

## 4. 推荐统一命名

建议统一为：

- `ApiResponse<T>`：统一 API 响应体。
- `ApiResponses`：统一 API 响应工厂方法。
- `ErrorCode`：业务错误码、默认消息和 HTTP 状态映射。
- `BusinessException`：可预期业务异常。
- `GlobalExceptionHandler`：全局异常转换器。

## 5. 具体需求包

### 5.1 正常流程

Controller 正常返回业务结果时，使用 `ApiResponses.success(data)` 创建 `ApiResponse<T>`。

无业务数据时，使用 `ApiResponses.success()` 创建 `ApiResponse<Void>`。

### 5.2 异常流程

Service 遇到可预期业务失败时，抛出 `BusinessException`。

全局异常转换器捕获 `BusinessException`、参数校验异常、请求体解析异常、参数类型异常和未知异常，并转换为统一响应结构。

### 5.3 权限与数据规则

本任务不实现登录和权限，只预留未登录与无权限错误码。

错误响应不得泄露密码、Cookie、Session ID、完整 JDBC URL、SQL、服务器路径或异常堆栈。

### 5.4 接口、配置和数据库要求

本任务不新增业务接口、不新增数据库表、不修改环境变量。

当前用于验证异常处理的临时 Controller 不应作为正式业务接口长期保留；后续应通过测试专用 Controller 或 Web 层测试覆盖异常映射。

### 5.5 测试场景

- `ApiResponses.success(data)` 返回业务码 `0`、消息 `ok` 和原始数据。
- `ApiResponses.success()` 返回业务码 `0`、消息 `ok` 和 `data=null`。
- `BusinessException` 可以携带 `ErrorCode` 与安全消息。
- 全局异常转换器按 `ErrorCode.httpStatus` 返回真实 HTTP 状态。
- 未知异常返回 `SYSTEM_ERROR`，客户端不包含异常类名或堆栈。
- Actuator 响应不被业务响应体包装。

## 6. 约束

- 不推进用户、文章、评论等业务模块。
- 不新增 Redis、RabbitMQ、Elasticsearch、Docker 或前端能力。
- 不把临时测试接口当作正式业务接口。
- 不提交只有编译通过但没有行为测试的公共异常处理实现。

## 7. 验收标准

- 设计文档和代码草稿使用同一套命名。
- `ApiResponse<T>`、`ApiResponses`、`ErrorCode`、`BusinessException` 和 `GlobalExceptionHandler` 职责边界清楚。
- 成功响应使用 `code/message/data` 三字段。
- 业务失败使用真实 HTTP `4xx/5xx` 状态。
- 参数校验错误第一版只返回首个安全消息。
- `./mvnw test` 至少执行统一响应与异常处理相关测试，并报告非零测试数量。
