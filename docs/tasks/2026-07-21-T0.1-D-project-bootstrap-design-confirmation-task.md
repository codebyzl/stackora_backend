# 2026-07-21 任务：T0.1-D 工程骨架健康检查设计确认

## 1. 任务目标

完成 Stackora V0 最小工程骨架健康检查设计的修订与开发者确认，为后续实现提供唯一、可测试且不泄露敏感信息的接口与验证边界。

本任务最终要交付的工程能力是：调用方能够通过 HTTP 状态和响应体区分应用自身可用与 MySQL 依赖不可用；开发者能够将不依赖本机 MySQL 的自动化测试与真实数据库连通性验证分开执行。

本任务的交付物是确认后的设计文档，不包含业务代码、数据库表、SQL、测试代码、依赖升级、Git 初始化或本地环境安装。

## 2. 用户价值

健康检查是后续注册、文章等所有业务接口的运行基础。明确故障语义可以避免数据库中断时接口返回假成功，也可以避免让开发者把本机数据库是否存在误当作自动化测试是否通过。

## 3. 需求范围与交付物

更新 `docs/modules/2026-07-14-project-bootstrap-design.md`，使其包含以下确定内容：

- `GET /api/health` 的 HTTP 状态、响应字段和无参数契约。
- `GET /api/health/database` 在 MySQL 可用与不可用时的 HTTP 状态、响应字段、错误码和无参数契约。
- 数据库探测调用链：`SystemHealthController -> SystemHealthService -> SystemHealthMapper -> SELECT 1`。
- 自动化测试与真实 MySQL 探测的 profile、命令和预期结果。
- Swagger / Knife4j 的本阶段边界。
- 现有 `User`、`UserMapper`、`UserService` 与示例查询测试不属于 V0 健康检查范围，后续工程骨架实现前必须移除或隔离，不得将其作为本阶段业务表或验收前提。
- 上述选择的理由、风险与验收方式。

推荐采用以下契约：

| 接口 | 条件 | HTTP 状态 | 最小响应字段 |
| --- | --- | --- | --- |
| `GET /api/health` | 应用可响应 | `200 OK` | `status=UP`、`application=stackora`、`profile`、`checkedAt` |
| `GET /api/health/database` | `SELECT 1` 成功 | `200 OK` | `status=UP`、`checkedAt` |
| `GET /api/health/database` | 连接、认证、库不存在或网络失败 | `503 Service Unavailable` | `status=DOWN`、`code=DATABASE_UNAVAILABLE`、`checkedAt` |

数据库不可用响应不得包含账号、密码、完整 JDBC URL、服务器路径、SQL 异常栈或底层异常消息。统一响应封装尚未建立时，本任务只固定以上字段，不提前引入业务通用响应类。

## 4. 正常与异常流程

### 4.1 正常流程

1. 应用读取当前激活 profile。
2. 调用方请求 `GET /api/health`，服务返回 `200 OK` 与应用状态信息。
3. 调用方请求 `GET /api/health/database`。
4. Controller 调用 Service，Service 调用 Mapper 执行 `SELECT 1`。
5. 查询成功时服务返回 `200 OK` 与数据库可用状态。

### 4.2 异常流程

1. 数据库连接失败、凭据无权限、数据库不存在或网络不可达。
2. Service 将底层失败转换为数据库不可用结果。
3. 接口返回 `503 Service Unavailable`、`DATABASE_UNAVAILABLE` 和非敏感状态字段。
4. 不返回假成功，也不将异常详情暴露给调用方。

必要环境变量缺失时，`dev` 或真实连通性验证应以可定位的配置错误失败；该失败不能被伪装成健康状态。

## 5. 权限、数据与配置规则

- 当前没有用户体系，两个接口均无需登录且只读。
- 不创建业务表，不写入业务数据，因此不涉及事务、数据归属、幂等写入或并发锁。
- 数据库名为 `stackora`；真实凭据只允许来自环境变量或未提交的本地配置。
- `mvn test` 必须只运行不依赖本机 MySQL 的单元或 Web 层测试。
- 真实 MySQL 探测必须通过明确的 `dev` 或后续独立 `integration` profile 执行；本任务不引入 Testcontainers。

## 6. 接口、配置与数据库要求

- 两个接口均为 `GET`，无请求参数，无业务表和无迁移脚本。
- 设计必须规定健康检查使用应用路由，而不是把当前 Actuator 端点直接等同于 `/api/health` 契约。
- `application.yaml`、`application-dev.yml` 与测试 profile 的职责必须在设计中区分：默认测试配置不要求真实数据源，真实探测配置从环境变量读取 MySQL 参数。
- Swagger / Knife4j 不在本任务实现；后续 V0 子任务再单独设计和接入。

## 7. 约束与非目标

保持项目标识：Maven 坐标 `com.victorzl:stackora`、Java 基础包名 `com.victorzl.stackora`、数据库名 `stackora`。若现有原型与这些标识不一致，记录为后续工程骨架实现前必须对齐的事项。

本任务不实现用户、文章、评论或其他业务模块；不将现有 `User` 原型实体、Mapper、Service 或固定记录数测试纳入 V0 骨架；不引入 Redis、Redisson、RabbitMQ、Elasticsearch、Docker、Nginx、前端、JWT、Sa-Token、Spring Security 或 Testcontainers；不复制 Paicoding 源码。

## 8. 测试场景与验收标准

- 设计文档对 HTTP 状态、响应字段、错误码、profile 与 Swagger 范围均只有一个明确结论，不保留开放选择。
- 设计定义 `GET /api/health` 的 `200` 路径，以及数据库可用的 `200` 和不可用的 `503` 路径。
- 设计定义数据库不可用响应的敏感信息边界。
- 设计定义一条不依赖本机 MySQL 的 `mvn test` 验证命令和一条真实 MySQL 探测命令，并给出各自预期结果。
- 设计仍限制在 V0 工程骨架，未新增业务表、业务接口或后续基础设施组件。
- 开发者确认修订后的设计文档；确认前不开始工程骨架编码。

## 9. Goal / Context / Constraints / Done when

**Goal**：确认健康检查接口和测试隔离的唯一契约。

**Context**：现有原型测试在默认 profile 启动数据源，缺少 `spring.datasource.url` 时失败；设计必须先明确自动化测试不依赖本机 MySQL 的边界。

**Constraints**：只修订设计文档；不修改 Java、YAML、POM、SQL 或本地环境；不扩大 V0 范围。

**Done when**：设计文档完成上述确定契约并由开发者明确确认。
