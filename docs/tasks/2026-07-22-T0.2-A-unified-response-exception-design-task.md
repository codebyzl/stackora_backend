# 2026-07-22 任务：T0.2-A 统一响应与异常处理设计

## 1. 任务目标

设计 Stackora 的统一成功响应、业务错误码、业务异常和全局异常转换规则，为后续用户注册、登录、文章和评论接口提供稳定、一致且不泄露内部信息的 HTTP 契约。

本任务最终要支撑的工程能力是：Controller 可以返回统一成功结构，Service 可以通过业务异常表达可预期失败，参数校验和未知异常可以被转换为明确的 HTTP 状态与安全响应体。

预计用时：1～3 小时。

## 2. 用户价值

API 调用方不需要为每个接口猜测不同的响应格式，可以稳定识别成功、参数错误、未登录、无权限、资源不存在、数据冲突和系统错误。开发者也可以将业务判断保留在 Service 层，而不是在每个 Controller 中重复编写异常捕获代码。

## 3. 明确能力与交付物

本次完成统一响应与异常处理的需求和技术设计，明确以下内容：

- `BaseResponse<T>` 的字段、泛型和序列化结构。
- `ErrorCode` 的编码、默认消息和 HTTP 状态映射。
- `BusinessException` 的创建方式和可暴露消息边界。
- `ResultUtils` 的成功与失败工厂方法。
- `GlobalExceptionHandler` 对业务异常、参数校验异常、请求体解析失败、参数类型错误和未知异常的转换规则。
- Jakarta Validation 的依赖边界：当前依赖树没有校验实现，后续实现阶段允许且只允许为本能力新增 `spring-boot-starter-validation`。
- Controller、Service、异常处理器之间的职责边界。
- Actuator 响应不进入业务统一响应封装。
- 单元与 Web 层测试场景、验收命令和预期结果。

## 4. 正常流程

1. Controller 接收并校验请求参数。
2. Controller 调用 Service 执行业务逻辑。
3. Service 正常返回业务结果。
4. Controller 使用 `ResultUtils.success(data)` 生成 `BaseResponse<T>`。
5. HTTP 返回 `200 OK`，响应体包含统一成功码、成功消息和业务数据。

## 5. 异常流程

- 参数校验失败：返回 `400 Bad Request` 和统一参数错误码。
- JSON 请求体无法解析：返回 `400 Bad Request`，不返回 Jackson 或 Java 内部异常信息。
- 参数类型不匹配：返回 `400 Bad Request`，消息指出合法的公开参数要求。
- Service 发现可预期业务失败：抛出 `BusinessException`，全局异常处理器按 `ErrorCode` 返回对应 HTTP 状态和响应体。
- 未知异常：服务端记录完整异常栈，客户端只收到 `500 Internal Server Error` 和通用安全消息。

## 6. 权限与数据规则

- 本任务不实现登录和权限校验，只预留未登录与无权限错误码。
- 错误响应不得包含密码、Cookie、Session ID、完整 JDBC URL、SQL、服务器路径或异常堆栈。
- 参数校验错误只暴露公开字段名和开发者定义的校验消息。
- 本任务不读写数据库，不涉及事务、并发、幂等或数据回滚。

## 7. 接口、配置与数据库要求

- 成功响应最小字段：`code`、`message`、`data`。
- 错误响应沿用同一结构，`data` 为 `null`。
- HTTP 状态必须表达协议语义，不能把所有错误都包装为 `200 OK`。
- 错误码使用稳定数字编码；HTTP 状态和业务错误码分别表达协议层与业务层语义。
- 不修改 Actuator 的 `/actuator/health` 与 `/actuator/info` 标准响应。
- 不新增数据库表、索引、SQL 或环境变量；生产依赖仅允许增加 `spring-boot-starter-validation`。

## 8. 约束

- 使用当前 `org.victor.stackora` 基础包和现有 Spring Boot 技术栈。
- 保持单体分层架构，不引入额外异常处理框架。
- Controller 不捕获通用 `Exception`。
- Service 不返回用于表达失败的 `null` 或魔法数字。
- 未知异常必须记录日志，但不得将底层异常消息直接返回客户端。
- 第一版保持响应结构最小，不提前加入 Trace ID、国际化、错误详情列表或多协议适配。

## 9. 非目标

- 不实现用户注册、登录、权限或业务 Controller。
- 不实现 JWT、Spring Security、Sa-Token 或统一认证。
- 不设计分页响应。
- 不实现日志链路追踪和全局 Trace ID。
- 不接入 Redis、RabbitMQ、Elasticsearch 或外部监控平台。
- 不修改数据库结构。

## 10. 测试场景

1. 成功响应可以正确序列化普通对象与 `null` 数据。
2. `BusinessException` 按错误码映射正确的 HTTP 状态、code 和 message。
3. Bean Validation 字段校验失败返回 400，且不泄露内部异常。
4. JSON 格式错误返回 400 和稳定错误结构。
5. URL 或查询参数类型错误返回 400。
6. 未知异常返回 500 和通用消息，同时服务端日志保留异常信息。
7. Actuator 健康响应保持 Spring Boot 标准结构，不被 `BaseResponse` 包裹。

## 11. 验收标准

- 设计中每种异常都有唯一的 HTTP 状态、业务错误码和安全消息规则。
- `BaseResponse<T>`、`ErrorCode`、`BusinessException`、`ResultUtils` 与 `GlobalExceptionHandler` 的职责没有重叠。
- 明确 Controller → Service → Exception Handler 的正常与异常调用链。
- 明确客户端响应与服务端日志的敏感信息边界。
- 测试清单覆盖成功、业务异常、参数错误、解析错误、类型错误、未知异常和 Actuator 兼容性。
- 不新增业务功能、数据库变更或后续基础设施组件。
- 开发者能够根据设计解释“HTTP 状态码”和“业务错误码”为什么需要同时存在。

## 12. Goal / Context / Constraints / Done when

**Goal**：形成可直接指导后续实现和测试的统一响应与异常处理契约。

**Context**：Stackora 工程骨架、环境配置、README 和 Actuator 健康检查已经建立，下一步需要先统一所有业务 API 的成功与失败表达方式。

**Constraints**：只完成需求与技术设计；不写业务 Controller，不改数据库；后续实现只允许增加 `spring-boot-starter-validation`；不包装 Actuator 响应。

**Done when**：设计文档完整定义响应模型、错误码、异常映射、分层职责、安全边界、测试场景和验收标准，并且不存在未决的核心接口契约。

## 16. 已确认设计决策

- 第一版统一响应只使用 `code`、`message`、`data` 三个字段。
- 业务失败使用真实 HTTP 4xx/5xx 状态，不将所有业务失败统一包装为 `200 OK`。
- 第一版参数校验错误只返回首个安全校验消息，不增加字段错误列表。
