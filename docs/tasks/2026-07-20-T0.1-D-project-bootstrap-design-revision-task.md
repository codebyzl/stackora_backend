# 2026-07-20 任务：T0.1-D 工程骨架设计修订与确认

## 1. 任务目标

完成 Stackora V0 最小工程骨架健康检查设计的修订与开发者确认，使后续实现具有唯一、可测试且不泄露敏感信息的接口和验证边界。

本任务的最终业务能力是：服务可区分应用可用与 MySQL 不可用，并为调用方和开发者提供一致的健康检查语义。交付物是确认后的模块设计，不包括 Maven 工程、业务代码、SQL、测试代码、Git 初始化或本地环境安装。

## 2. 用户价值

调用方能够从 HTTP 状态和响应体区分应用正常与数据库依赖故障；开发者能够稳定运行不依赖本机 MySQL 的基础测试，并在需要时显式验证真实 MySQL 连通性。将接口文档工具拆分出首个工程任务可避免基础骨架范围膨胀。

## 3. 需求范围与交付物

更新 `docs/modules/2026-07-14-project-bootstrap-design.md`，并明确以下内容：

- `GET /api/health` 的成功响应字段与 HTTP 语义。
- `GET /api/health/database` 的数据库可用和不可用响应字段、错误码与 HTTP 语义。
- 数据库探测调用链：`SystemHealthController -> SystemHealthService -> SystemHealthMapper -> SELECT 1`。
- `mvn test` 与真实 MySQL 连通性验证的隔离方式。
- Swagger / Knife4j 在本任务中的明确范围。
- 三项决策的理由与可验证的验收方式。

## 4. 推荐决策

1. 数据库探测不可用时返回 `503 Service Unavailable`，响应体使用 `DATABASE_UNAVAILABLE`；应用健康检查保持 `200 OK`。
2. `mvn test` 仅运行不依赖本机 MySQL 的单元或 Web 层测试；真实 MySQL 探测通过 `dev` 或独立 `integration` profile 的显式验证完成。Testcontainers 留待基础功能稳定后的独立任务。
3. Swagger / Knife4j 拆分为 V0 后续独立任务；当前任务只固定健康检查响应契约。

如采用替代方案，设计文档必须同时写明理由、调用方或测试影响，以及等价的验收方式。

## 5. 正常与异常流程

正常流程：服务读取当前 profile；`GET /api/health` 返回应用名、可用状态、当前 profile 和检查时间；`GET /api/health/database` 的 Mapper 成功执行 `SELECT 1` 后返回数据库可用状态。

异常流程：数据库连接失败、账号无权限、数据库不存在或网络不可达时，数据库探测返回明确的不可用结果，不返回假成功，不暴露密码、完整 JDBC URL、服务器内部路径或异常堆栈。必要环境变量缺失时，应用以可定位的配置错误失败。

## 6. 权限、数据、接口与配置规则

本阶段没有用户体系；两个接口均无需登录且只读。不创建业务表、不写入业务数据。开发数据库名为 `stackora`，数据库凭据仅从环境变量或未提交的本地配置取得。接口不接收请求参数，响应只包含状态判断所需的非敏感字段。

## 7. 约束与非目标

保持 Maven 坐标 `com.victorzl:stackora`、Java 基础包名 `com.victorzl.stackora` 和数据库名 `stackora` 不变。不实现用户、文章或其他业务模块；不引入 Redis、Redisson、RabbitMQ、Elasticsearch、Docker、Nginx 或前端；不复制 Paicoding 源码。

## 8. 测试场景与验收标准

- 模块设计文档不再保留上述三项开放选择，每项只有一个明确结论。
- 设计定义两个请求无参数接口的最小成功响应字段；数据库不可用时定义 `503`、`DATABASE_UNAVAILABLE` 与非敏感响应边界。
- 设计定义不依赖本机 MySQL 的 `mvn test` 范围，以及真实 MySQL 探测的显式 profile、命令和预期结果。
- 设计仍限制在 V0 最小工程骨架，未新增业务表、业务接口或后续基础设施组件。
- 开发者明确确认更新后的模块设计。
