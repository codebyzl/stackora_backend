# 2026-07-25 任务：T0.2-R 统一响应与异常处理评审及 Git 收尾

## 1. 任务目标

对统一响应与异常处理的已提交实现进行完整代码审查、测试验证和 Git 元数据检查，确保当前版本的公共响应与异常处理能力具备清晰边界，并形成可追溯的本地提交。

预计用时：1～2 小时。

## 2. 用户价值

统一响应与异常处理会被后续用户、文章、评论等接口直接复用。提交前完成代码和 Git 检查，可以避免把错误的提交说明、不完整的异常契约或无法重复验证的实现带入后续业务开发。

## 3. 当前版本能力

- 使用 `ApiResponse<T>` 表达业务接口响应。
- 使用 `ApiResponseFactory` 创建成功与失败响应。
- 使用 `ErrorCode` 维护业务码、默认消息和 HTTP 状态。
- 使用 `BusinessException` 表达可预期业务失败。
- 使用 `GlobalExceptionHandler` 转换业务异常和未知运行时异常。
- 使用测试专用 Controller 验证默认业务异常、自定义安全消息和未知运行时异常。

## 4. 当前版本边界

- `GlobalExceptionHandler` 当前只处理 `BusinessException` 和 `RuntimeException`。
- 参数校验、请求体解析失败和参数类型错误的专用映射推迟到参数校验能力接入时实现。
- `ApiResponse<T>` 使用 `JsonInclude.Include.NON_NULL`，当 `data` 为 `null` 时允许省略该字段。
- 本任务不增加用户、文章、评论、数据库表、缓存、消息队列或搜索能力。
- 本任务不修改 JDK、Spring Boot 或 MySQL 环境版本。

审查提交相对上一工程骨架提交新增的以下文件：

- 未知运行时异常是否只向客户端返回通用系统错误。
- 测试专用接口是否只存在于测试源码。
- Git 提交标题是否为规范的 Conventional Commit，而不是包含 Git 命令本身。

## 6. 正常与异常流程

### 6.1 正常流程

1. Controller 获得业务结果。
2. Controller 调用 `ApiResponseFactory.success(data)`。
3. 客户端收到 HTTP `200`、业务码 `0`、消息 `ok` 和业务数据。

### 6.2 业务异常流程

1. 业务代码抛出 `BusinessException`。
2. `GlobalExceptionHandler` 读取异常中的 `ErrorCode`。
3. HTTP 状态取自 `ErrorCode.httpStatus`。
4. 响应体返回对应业务码和安全消息。

### 6.3 未知运行时异常流程

1. Web 请求处理过程中出现未预期的 `RuntimeException`。
2. 服务端记录完整异常对象。
3. 客户端只收到 HTTP `500`、业务码 `99999` 和 `系统异常`。

## 7. 权限、数据与安全规则

- 本任务不涉及登录、权限、数据库读写、事务、并发或幂等。
- 自定义业务异常消息只能包含允许公开给客户端的业务描述。
- 客户端响应不得包含密码、Token、Cookie、Session ID、SQL、服务器路径或异常堆栈。
- 未知异常的底层消息不得直接写入响应体。
