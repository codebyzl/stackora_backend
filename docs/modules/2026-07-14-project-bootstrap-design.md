# Stackora V0 工程骨架与运行基线设计

## 1. 背景与目标

Stackora 是一个后端主导的技术社区项目，后续会持续增加用户、文章、评论、互动、通知、搜索和部署能力。V0 阶段的目标不是提前实现业务，而是建立可稳定启动、可安全配置、可测试、可观测、可持续扩展的 Spring Boot 后端基础。

工程骨架必须先解决以下基础问题：

- 本地开发、测试和后续部署环境的配置边界清晰。
- 数据库连接通过外部配置注入，仓库不保存真实凭据。
- 应用健康状态可以被开发者和部署环境稳定探测。
- Maven 构建、包结构、依赖选择和启动方式具备一致约定。
- 后续业务模块可以在统一工程基线上迭代，而不是每个模块各自处理启动、配置、健康检查和安全边界。

## 2. 范围

### 2.1 本次实现

V0 工程骨架包含：

- Spring Boot Web 后端应用。
- Maven 构建。
- MySQL 驱动与 MyBatis-Plus 基础接入。
- `dev`、`test` 等 profile 配置边界。
- 数据库连接参数通过环境变量或未提交本地配置注入。
- `.env.example` 提供变量名和示例值，不包含真实密码。
- Spring Boot Actuator 健康检查端点。
- 基础 README 与本地启动说明。
- 最小自动化测试框架入口。

### 2.2 本次不实现

本阶段不实现：

- 用户、文章、评论、点赞、收藏、关注等业务接口。
- 业务数据表、业务 SQL 和业务 Mapper。
- 自定义健康检查 Controller、Service 或 Mapper。
- Redis、Redisson、RabbitMQ、Elasticsearch。
- JWT、Sa-Token、Spring Security 或完整认证体系。
- Docker、Nginx、Kubernetes 或生产部署编排。
- 复杂前端页面。
- Paicoding 源码复制。

## 3. 企业级使用场景与需求

### 3.1 本地开发启动

后端开发者拉取项目后，应能根据 README 和 `.env.example` 配置本地 MySQL 连接信息，并使用统一命令启动应用。启动失败时，错误应能定位到 profile、环境变量、数据库连接或依赖问题，而不是依赖个人经验猜测。

### 3.2 自动化构建验证

开发者在提交代码前，应能执行 Maven 测试命令确认工程可编译、应用上下文可加载、关键基础能力未被破坏。测试不应默认依赖开发者本机必须存在某个特定数据库，否则会导致不同机器构建结果不一致。

### 3.3 运行健康探测

开发、联调或部署环境需要通过标准 HTTP 端点判断应用是否存活。基础阶段采用 Spring Boot Actuator 标准端点，避免在没有业务需要时重复实现自定义健康检查链路。

### 3.4 配置与凭据安全

数据库地址、账号、密码等敏感信息必须由环境变量或未提交的本地配置提供。示例文件只描述变量契约，不能包含真实凭据，也不能让测试环境误连生产或共享数据库。

### 3.5 后续模块承接

用户、文章和评论等模块只应关注业务模型、接口、事务和权限，不应重复处理工程启动、环境隔离、健康检查、Maven 构建和基础配置安全问题。

## 4. 工程规则

1. 应用必须能在明确 profile 下启动，不能依赖 IDE 隐式配置。
2. 真实数据库凭据不得进入 Git 跟踪文件。
3. `.env.example` 只提供变量名、用途和安全示例值。
4. 健康检查优先使用 Actuator 标准能力。
5. `mvn test` 应作为提交前最小验证命令。
6. 测试 profile 不应默认要求开发者本机 MySQL 可用；真实数据库连通性验证应通过单独的开发环境命令或后续集成测试方案完成。
7. V0 阶段不创建业务表，也不保留示例业务实体作为正式代码。
8. 新增生产依赖必须有明确用途，不能为了展示技术栈提前引入。

## 5. 正常运行流程

### 5.1 应用启动

```text
Developer / Runtime
  -> 设置 profile 与环境变量
  -> Maven 构建并启动 Spring Boot 应用
  -> Spring 加载 Web、Actuator、MyBatis-Plus 与数据源配置
  -> 应用监听 HTTP 端口
```

启动成功后，应用应打印清晰启动日志，并能访问已暴露的 Actuator 端点。

### 5.2 健康检查

```text
Client / Deployment Probe
  -> GET /actuator/health
  -> Spring Boot Actuator 聚合应用健康状态
  -> 返回标准 Actuator 响应
```

当本地配置额外设置 context path 时，访问路径按实际上下文前缀调整，例如 `/api/actuator/health`。

### 5.3 数据库连通性

当 profile 中配置了数据源并且应用成功创建连接池时，Actuator 可以通过数据源健康贡献者反映数据库可用性。数据库连通性验证属于运行环境验证，不在本阶段引入自定义业务 API。

## 6. 异常与故障场景

### 6.1 配置缺失

缺少数据库 URL、用户名或密码时，应用启动或健康检查应暴露可定位的配置问题。错误日志可以帮助开发者定位缺失变量，但不能打印真实密码。

### 6.2 数据库不可用

数据库未启动、库不存在、账号权限不足或网络不可达时，应用不得将数据库状态伪装为可用。Actuator 健康结果应能反映异常状态，具体细节暴露程度由 `management.endpoint.health.show-details` 控制。

### 6.3 测试环境不稳定

如果单元测试默认连接本地 MySQL，则不同开发者机器会出现不可重复结果。V0 阶段应将“可重复 Maven 测试”和“真实数据库探测”拆开验证。

### 6.4 凭据泄露

如果真实 `.env`、IDE 配置、YAML 或日志中出现数据库密码、完整 JDBC URL 等敏感信息，属于安全问题。仓库示例文件只能出现占位值。

## 7. 权限、数据与安全边界

- 本阶段没有用户体系，不涉及登录态、角色权限和数据归属。
- Actuator 健康端点只用于运行状态探测，不返回业务数据。
- 默认不向未授权调用方暴露完整健康详情。
- 不创建业务表，不写入业务数据。
- 日志不得输出数据库密码、Token、Cookie、Session ID 或完整连接串。

## 8. 数据模型

本阶段不创建业务表。

MySQL 在 V0 中只作为后续业务模块的数据源能力准备；业务表、唯一约束、索引、逻辑删除、自动填充等内容在对应模块单独设计。

## 9. 接口与运维端点

### 9.1 Actuator 健康端点

| 端点 | 方法 | 用途 | 响应结构 |
| --- | --- | --- | --- |
| `/actuator/health` | `GET` | 应用健康状态 | Spring Boot Actuator 标准响应 |
| `/actuator/info` | `GET` | 应用基础信息 | Spring Boot Actuator 标准响应 |

本阶段不定义 `/api/health` 或 `/api/health/database` 自定义接口。后续如出现平台级健康检查聚合需求，再单独设计自定义运维接口。

### 9.2 响应边界

Actuator 响应不使用业务统一响应结构包装。统一业务响应结构在后续“统一响应与异常处理”模块中定义，只应用于业务 API。

## 10. 配置设计

### 10.1 配置来源

- Git 跟踪文件：保存非敏感默认配置、profile 结构和占位变量。
- `.env.example`：保存环境变量契约和安全示例值。
- 本地 `.env` 或系统环境变量：保存真实数据库连接信息，不进入 Git。

### 10.2 Profile 职责

| Profile | 用途 | 数据库要求 |
| --- | --- | --- |
| 默认配置 | 公共非敏感配置 | 不保存真实凭据 |
| `dev` | 本地开发和真实数据库探测 | 允许通过环境变量连接本地 MySQL |
| `test` | 自动化测试 | 不应默认依赖开发者本机 MySQL |

### 10.3 管理端点配置

- 暴露 `health` 和 `info`。
- 健康详情默认不对未授权调用方全部公开。
- 后续生产部署阶段再根据实际访问控制方案收敛管理端点暴露范围。

## 11. 调用链与职责

V0 工程骨架没有业务调用链。基础职责划分如下：

```text
Spring Boot Application
  -> Web MVC
  -> Actuator Endpoint
  -> DataSource Health Contributor
  -> MySQL
```

- 启动类：负责启动 Spring Boot 应用。
- 配置文件：负责声明 profile、端口、数据源和管理端点。
- Actuator：负责标准健康检查。
- MyBatis-Plus：为后续 Mapper 和 Service 提供基础能力，本阶段不创建业务 Mapper。

## 12. 事务、并发与幂等

本阶段没有写操作，不需要事务。

健康检查和应用信息端点是只读能力，多次调用不应改变系统状态。当前阶段不需要 Redis、Redisson、分布式锁或消息队列。

## 13. 测试设计

### 13.1 自动化测试

自动化测试至少覆盖：

- Maven 编译成功。
- Spring 应用上下文可加载。
- Actuator 健康端点可访问。
- Actuator 响应保持标准结构。

### 13.2 本地运行验证

开发环境可执行：

```bash
./mvnw test
SPRING_PROFILES_ACTIVE=dev ./mvnw spring-boot:run
curl -i http://localhost:8080/actuator/health
curl -i http://localhost:8080/actuator/info
```

如果设置了 context path，应按实际前缀访问。

### 13.3 数据库异常验证

可在开发环境临时关闭 MySQL 或使用错误凭据，确认健康检查不会报告虚假的数据库可用状态，且响应和日志不泄露真实密码。

## 14. 验收标准

- 项目可以通过 Maven 构建。
- 应用可以在开发环境启动。
- `/actuator/health` 可访问并返回 Actuator 标准健康结构。
- `/actuator/info` 可访问。
- 数据库配置通过环境变量或未提交本地配置注入。
- Git 跟踪文件中没有真实数据库密码。
- 自动化测试不依赖本机必须存在某个特定 MySQL 实例。
- 本阶段没有正式业务表、业务接口或示例业务实体。
- 未引入 Redis、Redisson、RabbitMQ、Elasticsearch、Docker、Nginx 或前端实现。

## 15. Paicoding 预对比点

后续可对比 Paicoding 的以下工程能力：

- 工程目录组织。
- 配置文件拆分方式。
- Actuator 或自定义健康检查策略。
- MyBatis-Plus 基础配置。
- README 与本地启动说明。

当前项目不直接复制 Paicoding 源码。只有在本地存在可读取源码时，才对具体实现作证据化比较。

## 16. 风险与技术债

- 当前项目标识、包名和 Spring Boot 版本需要在正式业务模块开始前形成唯一权威约定。
- 如果测试长期没有行为断言，`mvn test` 只能证明编译，不足以证明工程骨架可靠。
- 本地 MySQL 由开发者自行配置，短期能降低环境成本，但后续需要引入更可重复的集成测试方案。
- Actuator 暴露范围在开发阶段可宽松，生产部署前必须重新审查访问控制和信息泄露风险。

## 17. 后续演进

V0 后续工程能力按以下顺序推进：

1. 统一响应与异常处理。
2. 参数校验与 Web 层测试。
3. MyBatis-Plus 分页、逻辑删除和字段填充策略。
4. Swagger / Knife4j 接口文档。
5. 数据库初始化脚本和基础测试完善。
